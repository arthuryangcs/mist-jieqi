# 重复局面裁判修正（2026-11-09）

## 已修正的问题

原实现只统计公开盘面与行棋方的出现次数，第三次出现就判最后落子方负。它既没有证明三个完整着法循环，也没有识别长将责任。两批JQE记录的六个重复终局全部因此处罚了应将方。

新实现不按最后一着分配责任。将死、困毙仍优先；根据连续公开盘面重建合法着法，核实三次完整循环，并检查每一着是否将军。只有单方在循环内每着都将军，才自动判该方长将负。无论最后落子的是长将方还是应将方，赢家一致。

## 依据与适用边界

- [2026年首届宁明花山双棋公开赛补充细则](https://m.gdchess.com/Show.asp?id=18106)，发布方为组委会，广象网刊载：执行2020版象棋规则；揭棋按原位首着、落子后揭子、暗俘仅吃子方可见；三次重复可申请裁决，长将外允许两回合变着。
- [2020版第23条公开转录](https://cnchess.net/rules/ChapterFiveSection23.html)：23.1–23.3要求双方着法循环三次；外来点首着计入，首着吃子不计；23.5.1单方长将立即判负；其他类别涉及变着程序。

另核对[2020中国象棋竞赛规则100页PDF镜像](https://qizhe.org.cn/home/wp-content/uploads/2025/04/2020%E4%B8%AD%E5%9B%BD%E8%B1%A1%E6%A3%8B%E7%AB%9E%E8%B5%9B%E8%A7%84%E5%88%99-2-1.pdf)第29页23.1–23.3/23.5.1、第44页图6。图6明确单方长将即使无法变着仍负。[齐津安判例讨论](https://qihome.org/qijinan/2024/04/15/thoughts-and-discussions-on-xiangqi-rules.html)的六回合三循环和外来点计数也支持该边界。PDF为第三方镜像，并非协会网站直接下载。

这是一套有公开赛事依据的规则选择，并非证明所有揭棋比赛都使用同一细则。[Pikafish社区《象棋程序竞赛规则》](https://www.pikafish.com/rule.html)使用第三次同局面即比较长将/长捉责任的另一套程序竞赛标准。本项目此次明确选择2020规则加上述揭棋赛事补充，不把十二半回合门槛说成所有程序比赛的通用要求。

当前实现自动处理的只是能从公开历史证明的单方长将。以下情况均不能冒充完整自动裁定：长捉、长杀、将杀捉组合、双边责任的优先关系、三点以上九回合、其他重复的两回合变着程序，以及规则图例中的例外。它们在完整重复成立时显示“重复待裁决”，允许继续合法走子，不直接判负或判和。应由适用赛事的裁判处理。

程序自动检测相当于内部发起裁判检查，没有实现棋手申请、裁判受理和申诉流程。原来的120闲步、400总步数是程序自己的简化上限，不是所引赛事的40回合自然限着；此次没有伪称一并实现完整赛事限着。在上限处仍处于待裁决重复的，标记未决而不是和棋。

## 计数、历史与信息边界

- 键只包含行棋方、每格棋子颜色、暗子公开原位角色或明子身份、明暗状态。
- 暗子真身、暗俘私有身份、随机种子不进入重复历史。
- 一个四半回合循环出现三遍需要十二个后继盘面。第三次出现同一盘面通常只有两个完整循环，不能等同于规则要求。
- 允许外来点非吃子首着计入；若首着吃子，不能以该窗口作出长将判罚。
- 必须核验窗口内每步合法，丢失历史、编辑导致历史不连续、纯计数堆出的伪重复均不能判负。
- 悔棋恢复原有证据，重新开局或编辑清除不再适用的历史。
- HTTP边界验证历史格式，不能通过附加历史字段夹带暗子真身。

## 搜索与外部对手

`engine.js` 的 `rootRules` 与实际走子使用同一裁判；`ai.js`、`native/bridge.mjs`、`native/search.cpp` 支持“本方长将负”和“对手长将、本方胜”两个方向。协议根结果为0无裁定、1和棋、2本方负、3本方胜、4揭子后逐样本核对总步数上限。总第400步的暗子根着不能统一判和：每个样本先检查将死/困毙，否则和棋，混合身份保留样本胜率，不偷看实际真身。

Pika等外部对手共用的 `safeRoots` 仅排除当前已经被证明立即判负的候选，在存在其他合法选择时使用；不足循环和待裁决不排除。棋子走法合法性与裁判后果分开，所有物理合法着仍能接受裁判检查。

深层搜索的重复路径不再返回固定0当和棋，而在先检查无合法着后用非终局静态估值截断，仍阻止含路径循环的结果写入普通置换表。这是防止无限搜索的近似，不是完整的深层长将/长捉证明，不能宣称搜索已经精确掌握所有竞赛重复规则。

旧实验使用冻结裁判和冻结核心才能复现原记录。它们的离线回放与当前默认引擎隔离；不能把旧结果自动“升级”为新裁判下的战绩。旧JQE试玩核心不能接收新根协议，保持关闭并拒绝旧版启动，待独立迁移验证。

## 历史影响

原始文件没有改动：

- `benchmarks/jqe/matches.json`：索引1、4、8的旧重复终局。
- `benchmarks/jqe-followup-2026-11-09/matches.json`：索引10、11、18的旧重复终局。

新规则逐着回放六局，到原终止点均没有终局，也未满足本实现的完整三循环条件。正确结论是应继续对局或按完整规则裁判，不能直接将旧胜负互换。旧批次5、10及新批次14、21曾经使用错误根候选过滤，虽然最终以将杀结束，也不能说不受影响。此前双方搜索还使用旧根分及内部重复和棋近似，因此不能只删除六局后宣布其余结果是新规则成绩。
