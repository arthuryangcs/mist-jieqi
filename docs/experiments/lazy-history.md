# 延迟私有历史表：2026-11-05 试验与 Pika 差距诊断

本轮有短响应收益，但没有持续搜索或棋力收益，**不默认启用**。生产源码、稳定二进制、试玩服务与用户棋局未更改。该代码仅作为可显式构建的独立实验保留，发布不代表推荐替换默认。

## 修改和被淘汰方案

在固定 C7/延迟稳定排序上，用共享只读零表代替每个 Search 提前清零的 16,200 项 uint32 历史表；第一次更新才分配原宽度的私有表。每份提前清零减少64,800字节。零表没有棋局信息且不可写，更新表不跨搜索上下文共享。评分算式、同分顺序、8个暗子样本、原HCE、全根覆盖、节点定义、取消/时间/栈保护不变。没有写死兵位或使用裁判暗子真值。

12次分阶段准备诊断：全暗准备约0.5–0.7ms，14根着约0.8ms，49根着快速制胜约2.2–2.6ms，159份前沿上下文约7.8–8.0ms；TT申请仅约0.002–0.22ms。准备只是总成本的一部分，不能把长期速度差全归于分配。首次诊断就绪约623ms，其余约5ms，原因未定位；就绪不计入搜索吞吐，原值保留。

先淘汰两个自有原型：16位历史表六局面×三轮固定工作综合速度比1.00457，未达预定1.02；占位表枚举综合1.000786，未达预定1.03，虽一个重残局约快5.2%，整体不采用。两项未混入本候选，源码和负结果均保留。

延迟历史表初筛：六局面固定工作综合速度比0.99138，最差0.9663；已知短控制25轮换序从8.383ms降至6.116ms，减少27.05%。通过的是事前固定的“短延迟至少快10%、长搜索综合不低于0.99、单例不低于0.95”筛选门槛，不是整体提速门槛。各根着评分一致，暗局节点一致，已知短控制均为168节点。

## Pika为什么在部分局面更快

固定版本是 [bcc83f88](https://github.com/brianhliou/pikafish-jieqi-wasm/tree/bcc83f88ee18760e60903d1a3aaa61ef6f70f2c9)，本机二进制SHA256为`f32d3c6dfe4d6d90da7728d9cc2af68c3195a1cefb1bc28f3829f174c518dba1`。对应源码`src/types.h:106`关闭NNUE，本次是HCE，不用AB的数据代替Pika。

源码事实：Pika在`position.cpp:546–573`展开概率身份，在`do_move`和`getDark`累计节点；Mist在Search.tick累计。Pika使用概率分支与选择性搜索，Mist保留八个采样世界和全根覆盖，工作量不能换算为“少/多八倍”。

Pika `movepick.cpp:180–237`分阶段生成吃子/安静着并局部插入排序；Mist已做延迟稳定排序但覆盖安排不同。Pika `tt.h:38–70`为3条10字节记录/32字节簇；64MiB理论6291456条。Mist全明根分区entryLimit合计约90000，八暗世界约720000，并使用完整128位键与观察者、库存、重复历史上下文。Pika共享表且跨手保留，Mist每请求重建私有上下文。本轮同局面测速每次新进程，与对弈中缓存状态不同。以上是容量/实现事实，不是已测命中率，也不能把理论容量比当实际加速比；改缓存仍须保留信息与循环上下文隔离。

另做24个自有子树CPU请求（6就绪控制、18搜索），未与比赛/测速并行。只用等待过的自有Node/引擎子树getrusage，未读取系统进程列表或附加其他进程；祖孙控制先验证计数。减去各引擎就绪CPU中位数估计搜索利用率，每组3次：

| 同一公共局面 | 候选平均满核等效 | Pika平均满核等效 |
|---|---:|---:|
| lazy-history-holdout/opening/1106001/0 | 3.644 | 3.999 |
| lazy-history-holdout/ending/1106426/0 | 1.806 | 4.006 |
| near-confirmation/ending/9711560/0 | 1.911 | 3.993 |

Pika接近4核，候选两个少根残局仅约1.8/1.9核，候选原生自报CPU提供独立交叉核对。就绪扣除仍含Node/关闭误差，个别子树估计略超4，不是多开搜索线程。结合任务分工源码，尾部等待是有证据的后续方向；尚未量化其独立因果贡献，不宣称节点成本已经完全一致。
